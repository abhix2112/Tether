**Your hands-on task (from LEARNING.md §8):** run the llm-d simulator, send one long prompt twice, and
watch `usage.prompt_tokens_details.cached_tokens` and time-to-first-token change.

```bash
# 1. Start the simulator (pinned image; no GPU, no tokenizer download).
docker run -d --name tether-sim0 --network host -e POD_IP=127.0.0.1 \
  ghcr.io/llm-d/llm-d-inference-sim:v0.11.2 \
  --model test-sim-model --port 8000 --enable-kvcache true \
  --block-size 64 --kv-cache-size 256 --max-model-len 16384 \
  --latency-calculator per-token --prefill-overhead 20ms --prefill-time-per-token 1ms \
  --inter-token-latency 5ms --seed 1 --mode random

# 2. Build a 2,000-word prompt.
python3 -c 'import json; print(json.dumps({"model":"test-sim-model","messages":[{"role":"user","content":" ".join(f"word{i}" for i in range(2000))}],"max_tokens":5,"stream":True,"stream_options":{"include_usage":True}}))' > /tmp/req.json

# 3. Send it twice. ttfb ≈ TTFT; the last line shows cached_tokens.
for i in 1 2; do
  curl -sN -w "\nrun$i ttfb=%{time_starttransfer}s\n" localhost:8000/v1/chat/completions \
    -H 'content-type: application/json' -d @/tmp/req.json | grep -E 'usage|ttfb'
done

# 4. Look at the cache metrics, then clean up.
curl -s localhost:8000/metrics | grep -E '^vllm:(prefix_cache|cache_config)'
docker rm -f tether-sim0
```

**Before you run it, predict:** the simulator's TTFT is `prefill_overhead + uncached_tokens × 1 ms`. The
prompt is 2,005 tokens and blocks are 64 tokens. What will `cached_tokens` be on run 2, and what TTFT?
(Hint: only *full* blocks are cached.) Then compare with what I measured in
[FINDINGS-M0.md](../FINDINGS-M0.md) §A2.

Things to try after: change one early word in the prompt and re-send (why does almost everything miss?);
change only the *last* word (why does almost everything still hit?). That is LEARNING.md §1.7 in action.

## Open questions

Decisions needed from the owner; each spec change goes in its own commit once agreed.

1. **The traces have no tool-vs-user labels (A7).** The canonical `062126` set has no `stop`,
   `input_kind` or `input_types` fields. Only the older `042026` set (739 traces, one model, 70 subagent
   groups) has `stop` and `input_types`. On 042026:
   - 87% of turns end in `tool_use`, 6% in `end_turn` and 8% with an empty stop;
   - gap length does **not** separate tool pauses from user pauses (p90 is 124 s for both), so no
     threshold heuristic works.

   Options:
   - **A (recommended):** simulate on 062126 and treat every main-turn gap as a tool pause (true for
     ≥ 87% of turns where we can check). Use 042026, which has ground truth, for the predictor prior,
     for E4, and for a sensitivity check that measures how much that assumption changes the E2 results.
   - B: use 042026 as the main simulation corpus. It is labelled, but has few subagents, an older CLI and
     one model, so H3 would need 062126 anyway.
   - C: ask SemiAnalysis for a v7 build with `stop` kept. It's outward-facing and slow; could be done in
     addition to A.
2. **There's no `Side` traffic in any trace (A7):** classifier and title calls were filtered out at the
   source. Proposal: side-call handling and fairness for `class=side` get measured only in live runs
   (E7), and §11.3 says so.
3. **ZMQ direction (A3/A10).** The sim always dials; vLLM binds when the endpoint has `*` and dials
   otherwise. Proposal: §6.2.4 says the gateway **binds** one SUB socket per worker and workers dial in.
   The map encoding is primary (vLLM v0.30.0 sends only maps; run the sim with
   `--use-vllm-map-event-format true`) and the legacy decoder stays as a fallback.
4. **§3.3 status is out of date (A9):** vLLM #53423 is **merged** but only adds plumbing, with no actions.
   #51381 first ships in v0.30.0. Proposal: update the table and pin vLLM v0.30.0 in §9.
5. **Usage details not in the spec (A5):**
   - OpenAI usage now has `prompt_tokens_details.created_cache_tokens`;
   - Anthropic streaming usage must be read from the **final** `message_delta`;
   - paths come with `?beta=true`.

   Proposal: add these to §6.2.1 and §6.1.7.
6. **Claude Code's per-request system-prompt hash (A11/vLLM docs)** would make every request look like
   a new program. Proposal: §6.1.2 normalization strips it. Its exact form is confirmed in the A8 capture.
7. **A measured LRU horizon (A6).** vLLM exports `vllm:kv_block_idle_before_evict_seconds`. Proposal:
   §6.1.6 uses it where available, and treats the event-rate estimate as a fallback and cross-check.
8. **For M5, not now:** 4–8B candidates have 32K–41K native context, while the AgentX median input is
   ~142K (reported). E6 must use a `--max-context` subset or RoPE scaling.
